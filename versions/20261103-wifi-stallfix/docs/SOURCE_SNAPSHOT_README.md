# 单摄图传卡顿修复候选 v0.2

日期：2026-11-03。此目录为独立候选，尚未烧录。

## 问题与证据边界

用户在 NX729J 手机上反馈：有效帧率约4至10帧，显示值约100至250毫秒，先出现有效帧率骤降，随后提示画面已过期，之后能自行恢复。这是用户观察，不是助手独立测量；旧网页显示值包含设备侧帧龄和请求耗时，不是完整的拍摄到屏幕延迟。

已确认的源码行为：旧版请求250毫秒即中止，失败后固定等120毫秒再请求；350毫秒无有效显示便提示过期。旧版丢弃迟到帧时不更新接收帧号，可能重复下载同一张旧JPEG。官方IDF 5.5.4 HTTP实现会将响应头拆为多次小块发送；旧版未设置TCP_NODELAY。是否确实发生Nagle与延迟ACK相互等待，仍需实机验证，不能认定为唯一根因。

## 最小修改

- HTTP连接建立时通过官方open_fn设置TCP_NODELAY，设置失败只关闭图传连接。
- 接收完成后推进接收帧号，迟到帧仍然丢弃，避免重复下载同一张旧JPEG。
- 请求连接期限由250毫秒调整为600毫秒；画面接收后仍按原300毫秒上界丢弃，350毫秒无新有效画面仍显示过期。600毫秒不是画面延迟目标，也不是允许显示旧帧的门槛。
- 请求错误后从20毫秒起重试，连续错误按40、80、160毫秒退避；正常空帧请求仍等待20毫秒，不并发堆请求。
- 增加/status里的输入帧数、已编码和丢弃帧数、发送/空响应/发送错误数、JPEG错误数和最近编码/发送耗时。发送耗时是服务器写入耗时，不是手机完整接收耗时。
- 网页将“设备帧龄”改称“帧龄估计”，说明包含请求耗时。
- 播放页增加默认收起的“查看连接信息”，展开后在前台继续播放时每2秒读取一次/status，显示输入、编码和发送速率。不再要求用户切换到新标签页看计数；切页会停止原图传页取图，使旧版编码计数停止，这样的观察不能用于判断摄像头故障。

只改main/wifi_preview.c和main/web/index.html。识别主源码、采集格式与帧率、L1/L2及灯控逻辑、分区、组件依赖保持与已烧入的v0.1一致。源码一致不能代替识别性能对照。
